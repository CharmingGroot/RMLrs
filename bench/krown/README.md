# KROWN with its own execution framework

[KROWN](https://github.com/kg-construct/KROWN) is the benchmark of the
KG-Construct community; its execution framework (`exectool`) runs each
engine in Docker and samples time, CPU and memory. This directory plugs
RMLrs into that framework without forking it.

| File | What |
|---|---|
| `rmlrs.py` | The `RMLrs` resource, copied into `execution-framework/bench_executor/` |
| `Dockerfile` | The RMLrs CLI image (`rmlrs-krown/rmlrs:dev`), built from this repository |
| `harness.Dockerfile` | Linux container for `exectool` itself (its collector is Linux-only) |
| `run.sh` | Builds the images, patches a temporary copy of the framework, runs and summarises |
| `summary.py` | Per-case table from the framework's results: median run, CPU, RAM, output digest |
| `watchdog.py` | Stops engine containers that were OOM-killed or run too long, so a run cannot hang |
| `compact.py` | Replaces finished runs' outputs by their digest (the framework keeps every output) |
| `mysql_case.py` | Turns a generated PostgreSQL case into the same case on MySQL (the generator writes no MySQL cases) |

```bash
git clone https://github.com/kg-construct/KROWN /path/to/KROWN   # tested at 824438c
cd /path/to/KROWN/data-generator
./exgentool generate --scenario=raw-RMLrs.json --root=/path/to/cases   # "engine": "RMLrs"
cd <RMLrs>
bench/krown/run.sh /path/to/KROWN /path/to/cases 3
```

Scenarios are generated by KROWN's own generator with `"engine": "RMLrs"`
or `"engine": "MorphKGC"`; nothing else in them changes.
A MySQL case is made from a generated PostgreSQL case (see the MySQL
results below):

```bash
bench/krown/mysql_case.py /path/to/cases/RMLrs/postgresql/<case> /path/to/mysql-cases/RMLrs/mysql/<case>
```

## What is changed, and why

The framework copy is patched in a temporary directory; nothing is
committed to KROWN. None of the changes touches what is measured.

- Container and network names get an `rmlrs-` prefix. The framework
  stops and removes any container with the name it is about to use; the
  prefix keeps it away from containers it did not start.
- Morph-KGC runs from an arm64 build of KROWN's own Morph-KGC Dockerfile,
  pinned to 2.10.0. The published `kgconstruct/morph-kgc:v2.2.0` image is
  amd64 only, and emulating it would not be a fair comparison. (KROWN's
  Dockerfile installs whatever Morph-KGC version is current, so "2.2.0"
  is only the image tag there.)
- Containers reach each other by their usual names ("PostgreSQL") through
  network aliases on the `rmlrs-bench_executor` network. Nothing is
  published on the host: the framework would otherwise bind 5432 on all
  interfaces. The harness container joins the same network to load the
  database, and PostgreSQL keeps its files in the case directory instead of
  `/tmp` of the Docker host.
- PostgreSQL runs from KROWN's own Dockerfile (`postgres:14.5-bullseye`),
  built for the host; `kgconstruct/postgresql:v14.5` is amd64 only.
- MySQL gets the same changes (name, files in the case directory, no
  published port) and runs from the official `mysql:8.0` image (8.0.46,
  Oracle Linux): KROWN's Dockerfile is `mysql:8.0-debian`, which is amd64
  only. The resource mounts its config file from a path inside the harness
  container, which the Docker daemon cannot see; it is copied into the case
  directory with mode 0644 (mysqld ignores a world-writable config file, and
  the resource sets umask 0).
- Morph-KGC's image gets SQLAlchemy as a last layer (needed for database
  scenarios since Morph-KGC 2.x), and `RMLRS_MORPH_PROCESSES` sets its
  `number_of_processes`.
- For database scenarios, the `RMLrs` resource turns KROWN's logical
  tables into RML database sources built from the connection parameters.
- psutil reports no CPU frequency inside Docker Desktop's arm64 VM; the
  collector only stores it as hardware information, so a missing value
  becomes -1.
- KROWN writes mappings in the legacy R2RML / old RML vocabulary. The
  `RMLrs` resource rewrites the vocabulary IRIs before starting the
  container (milliseconds, outside the measured container). The engine
  itself reads only the current vocabulary.

## Results · 2026-10-10 · raw data, Morph-KGC with 1 and 4 processes

The 2026-10-07 table ran Morph-KGC with the framework's configuration,
which has no `number_of_processes`; Morph-KGC then starts a pool of one
process per CPU (20 in this VM) and was OOM-killed on 1M rows. That says
more about the configuration than about the engine, so the raw scenario
was run again with the count set: `RMLRS_MORPH_PROCESSES=1` and `=4`
(`run.sh` writes it into Morph-KGC's configuration). Four processes leave
about 2 GB of the 8 GB VM per process, and fit (2.9 GB peak at 1M rows).

Same VM (10 CPUs, 8 GB) and method, same data for all engines, 3 runs,
median run; RMLrs at `9986dff` (after the duplicate-removal change).

| Members | Quads | Engine | Duration | CPU (user+system) | RAM (peak over baseline) |
|---|---|---|---|---|---|
| 100K | 2M | RMLrs | 2.44 s | 2.3 s | 3-20 MB |
| 100K | 2M | Morph-KGC, 1 process | 7.23 s | 7.3 s | 184-328 MB |
| 100K | 2M | Morph-KGC, 4 processes | 5.41 s | 9.8 s | 474-586 MB |
| 1M | 20M | RMLrs | 19.88 s | 17.4 s | 358 MB |
| 1M | 20M | Morph-KGC, 1 process | 59.74 s | 55.6 s | 1,412 MB |
| 1M | 20M | Morph-KGC, 4 processes | 40.29 s | 109.3 s | 2,956 MB |

- All runs of all three set-ups give the same output (2,000,000 and
  20,000,000 lines, same order-independent digest).
- At 100K the runs are short and RAM is the whole VM's, so the figures move
  a lot between runs; the range of the three runs is shown.
- RMLrs at 1M: 19.88 s here against 17.74 s on 2026-10-07 (other code, and
  the first of the three runs took 25.4 s). RAM went from 664 MB to 358 MB
  with the new duplicate-removal set.
- With the default configuration, Morph-KGC was also OOM-killed on
  2026-10-10 in the raw case with 1,000-character values (100K members × 20
  properties, a 2.0 GB CSV): the first run used all 8 GB of the VM, wrote
  1.17 GB of output and then waited at 0% CPU for 15 minutes until it was
  stopped by hand; the second run filled memory again within 3 minutes.
  (The framework's progress display lagged and named an earlier case;
  the result folders show which run was active.) `run.sh`
  now runs a watchdog (`watchdog.py`) that stops an engine container that
  Docker reports as OOM-killed or that runs longer than 10 minutes
  (`RMLRS_STEP_TIMEOUT`), so the framework records a failed step instead of
  waiting.

  a shared source once for all its triples maps is the obvious next step.
  *Correction (2026-10-11):* the RMLrs figure for `mappings_30_5` comes
  from a single run (the other two did not run while the disk was full);
  measured again with 3 runs it is 18.34 s against Morph-KGC's 27.05 s
  (below).
- The 1,000-character raw case (a 2.0 GB CSV) was left out: Morph-KGC with
  the default configuration filled the 8 GB VM on it (see above), and its
  outputs (more than 2 GB a run, kept for every run) did not fit on the disk.
  10M members and 5,000/10,000-character values were not run for the same
  reasons.
- The first attempt at these scenarios ran Morph-KGC with the framework's
  default configuration and was stopped when it hung (above); 17 of its
  cases had finished and are not reported, since the configuration differs.

## Results · 2026-10-14 · MySQL rows read as they arrive

The MySQL source now hands rows to the engine as the server sends them,
instead of collecting the whole result first. Reading this way, a join
could lose its connection: the engine indexed the parent on the first child
row, and while it read a large parent, the child's result stayed unread; a
MySQL server closes such a connection after `net_write_timeout` (60 s by
default). With the server at `--net-write-timeout=1`, a 100K-row child and
a 2M-row parent, reading rows as they arrive alone failed after 92,304 of
200,000 lines (`bytes remaining on stream`). The engine now builds the join
indexes before it opens a database child source, so no connection waits;
the same run then succeeds with the same output as before.

Same two cases on the Mac itself, the process alone (`/usr/bin/time -l`),
before (`793cb07`) and after alternating, 3 runs each, a `mysql:8.0`
container; same sorted output in every run:

| Case | Peak RSS before | Peak RSS after |
|---|---|---|
| raw_100000_20_0 | 109-184 MB | 78-90 MB |
| joins_perc_1-1_50.0 | 328-336 MB | 75-78 MB |
| raw, the 100K rows repeated 10 times (1M rows) | 340-411 MB | 71 MB |

- The 1M-row table repeats the same rows, so the output is the same 2M
  distinct lines; it shows that the memory no longer grows with the result.
- Wall time was not slower after in any pair (raw: 5.35-9.20 s before,
  3.95-4.68 s after; 1M rows: 31.1-38.8 s and 26.3-34.4 s), but the Mac was
